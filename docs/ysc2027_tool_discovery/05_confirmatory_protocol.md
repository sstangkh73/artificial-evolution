# เฟส 3: Protocol ของรันยืนยัน (ตรึงก่อนรัน)

จัดทำ: 14 ต.ค. 2569 (ysc-loop รอบ 7) · โครงการ YSC 2027 (29YCSS00443)
ต่อจาก `03_pilot_protocol.md` (แผนก่อนรัน pilot) และ `04_ผล_pilot.md` (ผล pilot)

**สถานะ: ตรึงแล้ว แต่ยังไม่ได้รัน** ผู้ใช้ต้องตรวจเอกสารนี้ก่อน ห้ามรัน seeds 5000+ จนกว่าผู้ใช้จะอนุมัติ หลังอนุมัติแล้วห้ามแก้เอกสารนี้หรือ `confirmatory_config.json` ถ้าจำเป็นต้องเปลี่ยน ให้เขียนเป็น deviation ในรายงานผลยืนยันพร้อมเหตุผล และรายงานผลทั้งแบบเดิมและแบบที่เปลี่ยน

รันยืนยันทดสอบสมมติฐานหลักข้อเดียว และตอบคำถามด้วยหลักฐานหลายด้านตามกฎในข้อ 6 ไม่ใช่ด้วยตัวเลขตัวเดียว

## 3. วิธีรัน
ใช้คำสั่งเดียวนี้ (Bash, จาก root ของ repo):
```
python scripts/run_tool_discovery.py --out data/tool_discovery_confirm_<วันที่รัน> \
  --conditions C0 C1 C2 C3 C4 --seeds 5000-5049 --ticks 1600 \
  --set immortal=true --set epsilon=0.05 --set q_init=0 --allow-confirmatory-seeds
```
เงื่อนไขของข้อมูลที่ใช้วิเคราะห์ได้ (ตรวจทุกข้อก่อนวิเคราะห์ และรายงานผลการตรวจ):

2. `code_tree` ของ `simulation` และ `world` ตรงกับที่ pilot S2 ใช้: `simulation = 2f579b41e1cdb8899fc07e9010a6b81583be3002`, `world = a872c386087928faa7ff2586cd1361b4558e7cb4` ถ้าไม่ตรง แปลว่าโค้ดของสนามหรือเอเจนต์เปลี่ยนหลัง pilot ห้ามใช้ข้อมูลนั้นเป็นผลยืนยัน (`scripts` เปลี่ยนได้ เพราะต้องเพิ่มสคริปต์วิเคราะห์ ดูข้อ 5)
3. `base_config` ใน `protocol.json` ต้องเท่ากับ `config` ใน `confirmatory_config.json` ทุกฟิลด์ (ยกเว้น `seed`/`condition`)

5. ห้ามรันซ้ำด้วย seeds อื่นหรือ config อื่นแล้วเลือกชุดที่ดูดีกว่า ถ้ามีการรันมากกว่าหนึ่งครั้ง ต้องรายงานทุกครั้ง และใช้ครั้งแรกที่ผ่านเงื่อนไข 1–4 เป็นผลหลัก

## 4. ตัวชี้วัด
คำนวณระดับรัน (1 seed × 1 เงื่อนไข) แล้วเทียบแบบจับคู่ตาม seed เหมือน 03 ข้อ 5 ทุกประการ ไม่เพิ่มหรือลดตัวชี้วัด
- **หลัก:** `final_net_per_alive_tick` = อาหารสุทธิต่อ agent-tick ในช่วง 25% สุดท้ายของรัน (อาหาร − แรง − ต้นทุนการสร้าง − ต้นทุนการเก็บ)
- **องค์ประกอบของตัวชี้วัดหลัก (รายงานเสมอ):** อาหาร − แรง ต่อ agent-tick (ฝั่งการหาอาหาร รวมทั้งการใช้เครื่องมือและการหามือเปล่า ไม่ได้แยกเฉพาะการใช้เครื่องมือ) (`final_food_per_alive_tick` − `final_effort` / `final_agent_ticks`), ต้นทุนการสร้างต่อ agent-tick, ต้นทุนการเก็บต่อ agent-tick คำนวณเหมือน `add_components` ใน `scripts/analyze_tool_discovery_pilot.py` และตรวจว่าผลรวมเท่ากับผลต่างหลัก
- **หลักฐานการค้นพบ:** `functional_rate`, `reuse_delta`, `rebuild_rate`, `first_discovery_tick` (RMST ที่ 1600 พร้อมสัดส่วนรันที่ค้นพบ)
- **รายงานทุกตัว ไม่ทดสอบ:** `functional_per_agent`, `rebuilds_of_functional_group`, `final_tool_use_rate`, `learning_gain`, `mean_final_energy`, `agents_ever_below_zero`, `mean_ticks_below_zero`, `level_a`, `level_b_run`

การตัดรัน (ตาม 03 ข้อ 5 เท่านั้น): `reuse_delta` ตัดรันที่ไม่มีคู่ฝั่งผลเสีย, `rebuild_rate` ตัดรันที่ตัวหารเป็นศูนย์ คู่ seed ที่ฝั่งใดฝั่งหนึ่งถูกตัดจะไม่ใช้ในคู่เทียบนั้น ต้องรายงานจำนวนคู่ที่ใช้จริงและจำนวนที่ตัดแยกตามเงื่อนไขทุกครั้ง ตัวชี้วัดอื่นต้องมีครบ 50 คู่ ถ้าไม่ครบถือว่าข้อมูลไม่สมบูรณ์ (ข้อ 3)

## 5. แผนสถิติ
ทุกการทดสอบเป็นแบบจับคู่ตาม seed ผลต่างคือ เงื่อนไขแรก − เงื่อนไขที่สอง ต่อ seed

**5.1 สมมติฐานหลัก (H1) หนึ่งข้อ ไม่ปรับ multiple comparisons**
- H1: ค่าเฉลี่ยของผลต่าง C1 − C2 ของ `final_net_per_alive_tick` > 0
- ทดสอบด้วย paired t-test สองทาง α = 0.05 (df = 49) H1 ผ่านเมื่อ p < 0.05 **และ** ค่าเฉลี่ยผลต่าง > 0
- รายงานคู่กัน: ค่าเฉลี่ยผลต่าง, SD, dz, bootstrap 95% CI (percentile, 10,000 รอบ, สุ่มเลือก seed แบบใส่คืน, `random.Random(0)`) และ sign count (จำนวน seed ที่ C1 > C2 / เสมอ / C1 < C2)
- ถ้า t-test กับ bootstrap CI ให้ข้อสรุปขัดกัน (เช่น p < 0.05 แต่ CI คร่อม 0) ให้รายงานทั้งคู่ตรง ๆ และถือว่า H1 **ไม่ชัดเจน**

**5.2 กลุ่มรอง ปรับด้วย Holm ภายในกลุ่ม (5 การทดสอบ, α รวม = 0.05)**
1. C1 − C0 ของ `final_net_per_alive_tick` (> 0)
2. C1 − C2 ของ `functional_rate` (ทิศที่สนับสนุน: > 0)
3. C1 − C2 ของ `reuse_delta` (> 0)
4. C1 − C2 ของ `rebuild_rate` (> 0)
5. C1 − C2 ของ `first_discovery_tick` (< 0 คือ C1 ค้นพบเร็วกว่า)

แต่ละข้อใช้ paired t-test สองทาง เรียง p จากน้อยไปมาก เทียบกับ 0.05/5, 0.05/4, … และหยุดที่ข้อแรกที่ไม่ผ่าน (Holm, 1979) ข้อที่ "ผ่าน" ต้องมีทั้ง p ที่ปรับแล้วผ่าน และผลต่างอยู่ในทิศที่ระบุ ข้อที่ p ผ่านแต่ผิดทิศ ให้รายงานว่าเป็นหลักฐาน **ค้าน** รายงาน bootstrap CI และ sign count ทุกข้อเหมือน 5.1

**5.3 เชิงพรรณนา (ไม่ทดสอบ รายงานค่าเฉลี่ย ผลต่าง และ bootstrap CI)**
- Gate A: C3 − C0 ของตัวชี้วัดหลัก พร้อมองค์ประกอบ
- Gate B: B1 (สัดส่วนรัน C0 ที่มี `n_functional_objects` ≥ 1) และ B2 (C3 − C0 ของ `functional_rate`)
- H5 ฝั่งการใช้: C1 − C4 ของ `final_net_per_alive_tick`, `final_tool_use_rate`, `functional_rate` (ห้ามอ้างว่า H5 ครอบคลุมการสร้าง 03 ข้อ 5)
- องค์ประกอบของ C1 − C2 และ C1 − C0
- ตัวชี้วัดในรายการ "รายงานทุกตัว ไม่ทดสอบ" ของข้อ 4 สำหรับ C1 − C2

**5.4 เครื่องมือวิเคราะห์**
ปัจจุบันมี bootstrap CI และ sign count ใน `scripts/analyze_tool_discovery_level_b.py`, `_paired_full` และ `t_cdf` ใน `scripts/analyze_tool_discovery_pilot.py` แต่ยังไม่มีสคริปต์ที่ทำ paired t-test + Holm ครบตามข้อนี้ สคริปต์วิเคราะห์ยืนยันต้อง **เขียน เทสต์ และ commit ก่อนรัน seeds 5000+** และทดลองรันได้เฉพาะกับข้อมูล pilot (`data/tool_discovery_pilot_s2_selected`) เท่านั้น การเขียนสคริปต์นี้ต้องไม่เปลี่ยนนิยามใด ๆ ในเอกสารนี้

## 6. กฎการสรุป "ค้นพบเครื่องมือ" (ตรึงจาก 03 ข้อ 8)
**กฎหลัก (ตาม 03 ข้อ 8 ทุกคำ):** สรุปว่า "สนับสนุนว่าเอเจนต์ค้นพบเครื่องมือ" เมื่อ (ก) H1 ผ่าน (ข้อ 5.1) และ (ข) หลักฐานการค้นพบอย่างน้อยหนึ่งด้าน (อัตราระดับ A = `functional_rate`, การใช้ซ้ำแบบเลือก = `reuse_delta`, การสร้างซ้ำ = `rebuild_rate`) มีค่าเฉลี่ยผลต่าง C1 − C2 ไปทางเดียวกับ C1 > C2 (คือ > 0) ถ้า H1 ผ่านแต่ (ข) ไม่จริง ให้สรุปว่า "C1 ได้อาหารสุทธิมากกว่า แต่ยังไม่มีหลักฐานว่ามาจากการค้นพบเครื่องมือ" ถ้า H1 ไม่ผ่านหรือไม่ชัดเจน ให้สรุปว่า "ไม่สนับสนุน"

**รายงานคู่กันเสมอ (เข้มกว่า ไม่ใช่กฎหลัก):** แต่ละด้านของ (ข) ผ่านการทดสอบในกลุ่มรองหลังปรับ Holm ในทิศที่สนับสนุนหรือไม่ (ข้อ 5.2 ข้อ 2–4), ด้านใดผ่านในทิศค้าน และ Gate A/B2 ในรันยืนยันผ่านหรือไม่ (ข้อ 5.3) เหตุผล: 03 ข้อ 8 ไม่ได้นิยามว่า "ไปทางเดียวกัน" ต้องมีนัยสำคัญหรือไม่ เอกสารนี้จึงคงความหมายตามตัวอักษรเป็นกฎหลัก (ไม่เปลี่ยนกฎหลังเห็น pilot) แต่บังคับให้รายงานแบบที่เข้มกว่าคู่กัน เพื่อให้ผู้อ่านเห็นว่าข้อสรุปแข็งแค่ไหน การรายงานนี้บันทึกเป็น deviation ข้อ 4 ใน `04_ผล_pilot.md` ถ้ากฎหลักผ่านแต่แบบเข้มไม่ผ่าน ต้องเขียนตรง ๆ ว่าหลักฐานการค้นพบไปทางเดียวกันแต่ไม่มีนัยสำคัญหลังปรับ multiple comparisons ถ้า Gate A หรือ B2 ไม่ผ่าน ต้องเขียนว่าสนามไม่ทำงานตามที่ออกแบบใน seeds ชุดนี้ ซึ่งทำให้ตีความผลได้จำกัด

กฎการรายงานองค์ประกอบ (ตาม 04 ข้อ 6 ไม่ใช่เกณฑ์ผ่าน/ไม่ผ่านใหม่): ใน pilot ผลต่างหลักราว 35% มาจากฝั่งการหาอาหาร (อาหาร − แรง) และราว 65% มาจาก C1 สร้างและเก็บน้อยกว่า รายงานยืนยันจึงต้องแสดงองค์ประกอบทั้งสามของ C1 − C2 พร้อม CI เสมอ และใช้ถ้อยคำดังนี้
- ถ้าขอบล่าง CI ของ อาหาร − แรง > 0: เขียนได้ว่า "เอเจนต์ที่เรียนจากผลจริงหาอาหารได้คุ้มกว่า (อาหาร − แรง)" พร้อมระบุสัดส่วนของผลต่างที่มาจากแต่ละองค์ประกอบ ห้ามเขียนว่าส่วนนี้มาจากเครื่องมืออย่างเดียว เพราะรวมการหามือเปล่าด้วย
- ถ้าไม่: ต้องเขียนว่าความได้เปรียบบนอาหารสุทธิมาจากการเลิกสร้าง/เก็บสิ่งที่ไม่คุ้มเป็นหลัก ซึ่งเป็นการเรียนรู้จากผลจริงแต่ไม่ใช่การหาอาหารที่ดีกว่า
- ไม่ว่ากรณีใด ต้องรายงาน `final_tool_use_rate` คู่กัน (สัดส่วนของการใช้ในช่วงท้ายที่ใช้วัตถุ ไม่ใช่ต่อ tick; ใน pilot C1 ต่ำกว่า C2 ทุก seed) ห้ามเขียนว่า "C1 ใช้เครื่องมือมากกว่า" ถ้าข้อมูลไม่แสดงเช่นนั้น

## 7. สิ่งที่ผลยืนยันจะบอกได้และบอกไม่ได้
- บอกได้: ในสนามและ config นี้ learner ที่ได้สัญญาณจากผลจริง (C1) ทำได้ดีกว่า learner ตัวเดียวกันที่ได้สัญญาณสุ่ม (C2) หรือไม่ และมีร่องรอยการค้นพบ (อัตราวัตถุที่ใช้ได้, การใช้ซ้ำแบบเลือก, การสร้างซ้ำ) หรือไม่
- บอกไม่ได้: ผลที่ค่า ε, q_init หรือจำนวน tick อื่น (เลือกเพียงเซลล์เดียวจาก grid), ผลเมื่อเอเจนต์ตายได้ (รันนี้เป็นอมตะ), ผลในสนามอื่น หรือการค้นพบในความหมายที่กว้างกว่ากลไกของ learner นี้

## 8. ข้อจำกัดที่ทราบก่อนรัน (ต้องเขียนในรายงานยืนยัน)
1. Gate B1 ผ่านง่าย (100% ทุกเซลล์ใน pilot) จึงแยกแยะไม่ได้ ข้อที่แยกแยะได้จริงคือ B2
2. `feature_key` (กลุ่มสมบัติที่ปัดเป็นช่วงกว้าง 3) เป็นการจัดกลุ่มที่ผู้วิจัยออกแบบ เป็นสมมติฐานของงาน learner ไม่เห็นคะแนนฟิสิกส์ เกณฑ์ หรือชื่อเครื่องมือ (เฉพาะ C3 ที่อ่านผ่าน `OracleView`)
3. ลำดับสุ่มของนโยบายผูกกับชื่อเงื่อนไข C1 กับ C2 จึงไม่ได้ใช้ลำดับสุ่มของนโยบายร่วมกัน เพิ่มความแปรปรวนแต่ไม่ทำให้เอนเอียง
4. สัญญาณเรียนรู้คือ อาหาร − แรง ของการใช้แต่ละครั้ง ไม่รวมต้นทุนการสร้าง แต่ตัวชี้วัดหลักรวม จึงต้องรายงานองค์ประกอบ (ข้อ 6)
5. ระดับ A ตรวจทุก prefix ของประวัติการใช้และใช้ baseline ต่อรัน (ทดสอบหลายครั้ง) จึงเป็นหลักฐานรอง
6. `reuse_delta` และ `rebuild_rate` เป็นค่าแบบมีเงื่อนไข (ตัดรันที่ตัวหารเป็นศูนย์) การตัดขึ้นกับพฤติกรรมในรัน จึงอาจไม่สุ่ม และคู่ที่เหลืออาจไม่ใช่ประชากรเดียวกับทั้ง 50 seeds paired t-test ของสองตัวนี้จึงตีความได้เฉพาะ "ในรันที่วัดได้" ต้องรายงานจำนวนที่ตัดแยกตามเงื่อนไข (pilot S2 ตัด `rebuild_rate` 1 คู่) `reuse_delta` ไม่มีความหมายสำหรับ C3
7. `first_discovery_tick` ใช้ baseline มือเปล่าที่คำนวณจากทั้งรัน รวมข้อมูลหลัง tick ที่นับว่าค้นพบ (ฝั่งผู้วิเคราะห์ ไม่ใช่สิ่งที่เอเจนต์เห็น) จึงไม่ใช่เวลาค้นพบแบบ real-time และรันที่ไม่ค้นพบถูกนับที่ 1600 (RMST) paired t-test บนค่านี้เป็นการประมาณ ต้องรายงานสัดส่วนรันที่ค้นพบคู่กัน
8. C0 สร้างวัตถุแทบทุก tick ที่ว่างเมื่อเป็นอมตะ คู่เทียบกับ C0 บนอาหารสุทธิจึงสะท้อนต้นทุนการสร้างมาก ต้องดูองค์ประกอบ
9. เซลล์ถูกเลือกจาก 16 เซลล์ด้วยสมรรถนะของ C1 ใน S1 ค่าของ C1 บน S2 (0.397) ใกล้ S1 (0.398) แต่ยืนยันไม่ได้ว่าไม่มี selection bias รันยืนยันใช้ seeds ใหม่ทั้งหมดจึงไม่ได้รับผลจากการเลือกนี้ในการทดสอบ H1
10. ผลของ pilot บน S2 (C1 − C2 = 0.279, dz 1.51) ทำให้ power ที่ n = 50 สูงมาก ถ้า H1 ไม่ผ่านในรันยืนยัน ต้องรายงานตรง ๆ และไม่รันเพิ่มเพื่อหาผลที่ผ่าน

## 9. สิ่งที่ห้ามทำ
- ห้ามรัน seeds 5000+ ก่อนผู้ใช้อนุมัติ และห้ามใช้ seeds 5000+ ในการเลือกค่าหรือแก้โค้ดใด ๆ
- ห้ามเปลี่ยนตัวชี้วัดหลัก คู่เทียบหลัก กลุ่มรอง วิธีปรับ multiple comparisons หรือกฎข้อ 6 หลังเห็นผลยืนยัน
- ห้ามตัดรันหรือ seed นอกเหนือจากกฎในข้อ 4
- ห้ามแก้ `simulation/` หรือ `world/` ระหว่างการเขียนเอกสารนี้กับการรันยืนยัน (ตรวจด้วย `code_tree` ในข้อ 3)
- ห้ามรายงานเฉพาะตัวชี้วัดที่ดูดี ต้องรายงานครบทุกตัวในข้อ 4 รวมตัวที่ไม่สนับสนุน (ใน pilot คือ `rebuilds_of_functional_group`, `learning_gain`, `final_tool_use_rate`)
