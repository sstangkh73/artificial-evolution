# เฟส 3: Pilot protocol (เขียนและ commit ก่อนรัน pilot)

จัดทำ: 14 ต.ค. 2569 (ysc-loop รอบ 3) · โครงการ YSC 2027 (29YCSS00443)
โค้ด: `simulation/tool_discovery.py`, `simulation/tool_discovery_metrics.py`, `scripts/run_tool_discovery.py`, `scripts/analyze_tool_discovery_level_b.py`

เอกสารนี้กำหนดทุกอย่างที่ pilot จะทำ **ก่อน** เห็นผล pilot ถ้าต้องเปลี่ยนสิ่งใดหลังเห็นผล ต้องบันทึกเป็น deviation พร้อมเหตุผลใน `04_ผล_pilot.md` ห้ามแก้ไฟล์นี้ย้อนหลัง

## 1. คำถามและหน้าที่ของ pilot
คำถามวิจัย: เอเจนต์ค้นพบเครื่องมือได้หรือไม่ จากการลองผิดลองถูก โดยไม่มีสูตร ชื่อเครื่องมือ หรือคะแนนประโยชน์ให้ล่วงหน้า

pilot **ไม่ได้** ตอบคำถามนี้ pilot มีหน้าที่ 3 อย่างเท่านั้น
1. เลือกค่าการสำรวจของ learner (ε, q_init) และจำนวน tick ตามกฎในข้อ 6
2. ตรวจ Gate A และ Gate B (ข้อ 5) ว่าสนามทดลองใช้ทดสอบคำถามได้จริง
3. ประมาณขนาดผลของคู่เทียบหลัก C1−C2 เพื่อคำนวณจำนวน seed ของรันยืนยัน (power analysis, ข้อ 7)

ผล pilot ทั้งหมดเป็นเชิงพรรณนา ห้ามนำไปอ้างเป็นหลักฐานการค้นพบเครื่องมือ

## 2. ค่าคงที่ทุกเซลล์
- `immortal: true` (ผู้ใช้ตัดสิน 14 ต.ค.): ไม่มีการตาย พลังงานติดลบได้เป็นบัญชี และไม่ใช้เกณฑ์พลังงานสำรองก่อนสร้าง ดังนั้น "ต่อ tick ที่ยังมีชีวิต" ในชื่อตัวชี้วัดเท่ากับ "ต่อ agent-tick" ทุกเงื่อนไข ปัญหา survivor bias ในเอกสาร 02 ข้อ 6.1 จึงหมดไปโดยการออกแบบ
- เงื่อนไข C0, C1, C2, C3, C4 ครบทุกเซลล์ บน seed ชุดเดียวกัน (จับคู่ตาม seed)
- ค่าอื่นของ `ArenaConfig` ใช้ค่าเริ่มต้นในโค้ดที่ commit แล้ว (20 เอเจนต์, กริด 40×40, α = 0.2, `feature_bin_width` = 3, ฯลฯ)
- รันจากโค้ดที่ commit แล้วเท่านั้น (`git status` ของ `simulation/ world/ scripts/` สะอาด, runner บันทึก `code_dirty: false`) ห้ามใช้ `--allow-dirty`

## 3. Seeds
- seeds 0–99 ใช้ไปแล้วใน smoke/calibration ห้ามใช้เลือกค่า
- pilot ใช้ seeds 1000–1099 เท่านั้น แบ่งเป็น 2 ส่วนที่ไม่ซ้อนกัน
  - **ส่วนเลือกค่า (S1): seeds 1000–1049** ใช้เลือกเซลล์และตรวจ Gate
  - **ส่วนประมาณผล (S2): seeds 1050–1099** รันเฉพาะเซลล์ที่เลือกแล้ว ใช้ประมาณขนาดผลสำหรับ power analysis
  การแยกนี้กันไม่ให้ขนาดผลที่ใช้คำนวณ power ถูกขยายเกินจริงจากการเลือกเซลล์ที่ดีที่สุด (winner's curse)
- seeds 5000 ขึ้นไปสงวนไว้สำหรับรันยืนยัน ห้ามแตะในเฟสนี้

## 4. Grid (ส่วน S1)
| พารามิเตอร์ | ค่า | เหตุผล |
|---|---|---|
| ε (`epsilon`) | 0.05, 0.10, 0.20, 0.30 | 0.10 คือค่าเดิม เอกสาร 02 ข้อ 6.3 สงสัยว่าคอขวดอยู่ที่การสำรวจ จึงขยายขึ้นไปถึง 0.30 |
| q_init | 0, 10 | 0 คือค่าเดิม; 10 สูงกว่าผลสุทธิที่ได้จากการใช้เครื่องมือครั้งเดียวเกือบทุกกรณี (สัญญาณเรียนรู้ = อาหาร − แรง, ผลสำเร็จสูงสุด 9 + มือเปล่า) จึงเป็นค่าเริ่มแบบ optimistic ที่บังคับให้ลองทุกทางเลือกก่อน |
| จำนวน tick | 800, 1600 | 800 คือค่าเริ่มต้น; 1600 ใช้ดูว่า learner ยังเรียนไม่อิ่มตัวหรือไม่ |

S1 รวม 4 × 2 × 2 = 16 เซลล์ × 5 เงื่อนไข × 50 seeds = 4,000 รัน, S2 อีก 5 × 50 = 250 รัน, รวมทั้ง pilot 4,250 รัน (รันละประมาณ 0.2–0.5 วินาที)
C0 และ C3 ไม่ใช้ ε และ q_init แต่รันซ้ำในทุกเซลล์เพื่อให้แต่ละโฟลเดอร์จับคู่ seed ได้ครบในตัว (ค่า C0/C3 ในเซลล์ที่ tick เท่ากันควรเท่ากันทุกตัว ใช้เป็นการตรวจความถูกต้องของ runner ได้)

**ไม่รวม softmax τ** แม้แผนขั้น 4 จะเอ่ยถึง เพราะ learner ในโค้ดใช้ ε-greedy เท่านั้น การเพิ่ม softmax คือการเพิ่มกลไกใหม่ที่ยังไม่ได้ทดสอบ และ q_init แบบ optimistic ทำหน้าที่เพิ่มการสำรวจแบบมีทิศทางอยู่แล้ว จึงตัดออกเพื่อให้ grid เล็กและโค้ดไม่เปลี่ยนระหว่าง pilot (บันทึกเป็นการตัดสินใจ ไม่ใช่ deviation เพราะตัดสินก่อนรัน)

คำสั่งรัน (Bash, หนึ่งโฟลเดอร์ต่อหนึ่งเซลล์ แทนค่าใน `{}` ให้ครบ แบ่งรันหลายรอบได้ด้วย `--resume`):
```
python scripts/run_tool_discovery.py --out data/tool_discovery_pilot_s1_e{ε×100:03d}_q{q_init}_t{ticks} \
  --conditions C0 C1 C2 C3 C4 --seeds 1000-1049 --ticks {ticks} \
  --set immortal=true --set epsilon={ε} --set q_init={q_init}
```
เช่น `data/tool_discovery_pilot_s1_e010_q0_t800` ส่วน S2 ใช้ `data/tool_discovery_pilot_s2_selected` กับ seeds 1050–1099 และค่าของเซลล์ที่เลือก

## 5. ตัวชี้วัดและ Gate
ทุกค่าคำนวณระดับรัน (1 seed × 1 เงื่อนไข = 1 หน่วย) แล้วเทียบแบบจับคู่ตาม seed ภายในโฟลเดอร์เดียวกัน ด้วย `scripts/analyze_tool_discovery_level_b.py` (bootstrap 95% CI ของค่าเฉลี่ยผลต่าง, 10,000 รอบ, สุ่มเลือก seed)

**ตัวชี้วัดหลัก:** `final_net_per_alive_tick` = อาหารสุทธิต่อ agent-tick ในช่วง 25% สุดท้ายของรัน (อาหาร − แรง − ต้นทุนการสร้าง − ต้นทุนการเก็บ) รายงานองค์ประกอบทุกตัวคู่กัน

**คู่เทียบหลัก:** C1 − C2 บนตัวชี้วัดหลัก — learner ตัวเดียวกัน ต่างกันที่สัญญาณเรียนรู้จริงกับสัญญาณที่ถูกสุ่ม ถ้า C1 ดีกว่า แปลว่าผลมาจากการเรียนรู้จากผลจริง ไม่ใช่จากกลไกการเลือกหรือโอกาสเจอวัตถุ

ข้อจำกัดที่ทราบก่อนรัน (จากการรีวิวของ Codex):
- สัญญาณเรียนรู้ของ learner คือ อาหาร − แรง ของการใช้แต่ละครั้ง (`_learning_signal(net)`) ไม่รวมต้นทุนการสร้างและการเก็บ แต่ตัวชี้วัดหลักรวมต้นทุนเหล่านั้น จึงรายงาน C1 − C2 ของ "อาหาร − แรง ช่วงท้ายต่อ agent-tick" (`final_food_per_alive_tick` − `final_effort` / `final_agent_ticks` เพราะ `final_effort` เป็นผลรวม ไม่ใช่ค่าต่อ tick) คู่กันเสมอ เพื่อแยกว่าผลต่างมาจากฝั่งการใช้หรือฝั่งต้นทุนการสร้าง
- seed เดียวกันให้เส้นทางเดิน การเจออาหาร และตำแหน่งเกิดเหมือนกันทุกเงื่อนไข แต่ลำดับสุ่มของนโยบาย (การสำรวจ, การตัดสินเสมอ) ผูกกับชื่อเงื่อนไขด้วย C1 กับ C2 จึงไม่ได้ใช้ลำดับสุ่มของนโยบายร่วมกัน สิ่งนี้เพิ่มความแปรปรวนแต่ไม่ทำให้เอนเอียง (ทั้งสองเงื่อนไขสุ่มจากการแจกแจงเดียวกัน) และถูกรวมอยู่ใน SD ที่ใช้คำนวณ power แล้ว ไม่แก้โค้ด เพราะค่าเริ่มต้นต้องให้ผล smoke เดิม
- สิ่งที่ learner เห็นตามโค้ด: กลุ่มสมบัติที่รับรู้ได้แบบหยาบ (`feature_key`, ปัดเป็นช่วงกว้าง 3), รหัสวัตถุ, จำนวนครั้งที่ใช้, พลังงานของตัวเอง, วัสดุที่ถือ และบริบทอาหาร (ดู `01_information_access_map.md`) ไม่เห็นคะแนนฟิสิกส์ เกณฑ์ หรือชื่อเครื่องมือ มีเพียง C3 ที่อ่านคะแนนผ่าน `OracleView` ส่วน `feature_key` เป็นการจัดกลุ่มที่ผู้วิจัยออกแบบ ซึ่งเป็นสมมติฐานของงานนี้ที่ต้องเขียนในรายงาน

**หลักฐานการค้นพบ (รอง, รายงานทุกตัว ไม่เลือกเฉพาะตัวที่ดูดี):**
- ระดับ A แบบอัตรา: `functional_rate` (วัตถุที่ผ่านระดับ A / วัตถุที่สร้าง) และ `functional_per_agent`; ส่วน `level_a` แบบผ่าน/ไม่ผ่านเป็นเชิงพรรณนาเท่านั้น เพราะ smoke พบว่าผ่านทุกเงื่อนไขรวม C0
- การใช้ซ้ำแบบเลือกได้: `reuse_delta` = อัตราใช้กลุ่มสมบัติเดิมซ้ำหลังผลดี − หลังผลเสีย (รันที่ไม่มีคู่ฝั่งผลเสียจะถูกตัดและรายงานจำนวนที่ตัดแยกตามเงื่อนไข ค่านี้จึงเป็นค่าแบบมีเงื่อนไข "ในรันที่มีทั้งสองฝั่ง" ถ้าจำนวนที่ตัดต่างกันมากระหว่างเงื่อนไข ต้องระบุว่าเปรียบเทียบได้จำกัด)
- การสร้างซ้ำ: `rebuild_rate`, `rebuilds_of_functional_group`
- เวลาถึงการค้นพบครั้งแรก: `first_discovery_tick` โดยรันที่ไม่พบ = ค่า `ticks` ค่าเฉลี่ยจึงเท่ากับ restricted mean time (RMST) ที่ขอบเขต `ticks` ซึ่งเป็นตัวสรุปที่ใช้ได้กับข้อมูล censored รายงานคู่กับสัดส่วนรันที่ค้นพบภายในรัน
- ระดับ B ระหว่างเงื่อนไข: ผลต่าง C1 − C2 และ C1 − C0 ของ `reuse_delta` และ `rebuild_rate` (`level_b_run` เป็นแค่ตัวคัดกรองรายรัน เพราะผ่านได้แม้ใน C2)
- รอง: `final_tool_use_rate`, `learning_gain`, `mean_final_energy`, `agents_ever_below_zero`, `mean_ticks_below_zero`

baseline มือเปล่าในการตัดสินระดับ A คำนวณจากข้อมูลทั้งรันฝั่งผู้วิเคราะห์ เอเจนต์ไม่เห็นค่านี้ จึงไม่ใช่การรั่วของข้อมูล oracle เข้าสู่เอเจนต์ ข้อจำกัด: baseline คำนวณแยกต่อรัน (ใช้ข้อมูลทั้งรัน) และระดับ A ตรวจทุก prefix ของประวัติการใช้ ซึ่งเป็นการทดสอบหลายครั้ง วัตถุที่ถูกใช้บ่อยจึงมีโอกาสผ่านโดยบังเอิญมากขึ้น ระดับ A จึงเป็นหลักฐานรอง ไม่ใช่ตัวตัดสินหลัก

การวิเคราะห์ทำเฉพาะโฟลเดอร์ที่ manifest ระบุว่ารันครบ (`completed_runs == expected_runs`, `missing` ว่าง) และต้องรายงานจำนวนคู่ seed ที่ใช้จริง (ต้องเป็น 50 ต่อคู่เทียบ ยกเว้นตัวชี้วัดที่ตัดตามกฎข้างบน)

**เรื่อง C0 กับต้นทุนการสร้าง:** เมื่อเป็นอมตะ C0 สร้างวัตถุแทบทุกครั้งที่ว่าง (ไม่มีเกณฑ์พลังงานสำรอง) อาหารสุทธิของ C0 จึงติดลบจากต้นทุนการสร้าง ไม่ใช่เพราะเลือกเครื่องมือผิดอย่างเดียว ตัดสินว่า **คง C0 ไว้ตามนิยาม** (นโยบายสุ่มคือสิ่งที่ควรเป็น) แต่คู่เทียบที่เกี่ยวกับ C0 บนอาหารสุทธิจะรายงานพร้อมองค์ประกอบเสมอ และ Gate B ใช้ `functional_rate` ซึ่งไม่ขึ้นกับจำนวนครั้งที่สร้าง

**Gate A (oracle ทำงานได้):** ในเซลล์นั้น ผลต่างจับคู่ C3 − C0 ของ `final_net_per_alive_tick` มีขอบล่างของ 95% CI > 0 (รายงานผลต่างของอาหาร − แรง และต้นทุนการสร้างคู่กัน เพื่อดูว่า Gate ผ่านเพราะ oracle ใช้เครื่องมือได้ดี หรือแค่เพราะหลีกเลี่ยงต้นทุนการสร้าง)

**Gate B (C0 ไม่เป็นศูนย์และไม่ง่ายเกินไป):** ทั้งสองข้อต้องจริง
- B1 ไม่เป็นศูนย์: อย่างน้อย 20% ของรัน C0 มี `n_functional_objects` ≥ 1 (การสุ่มเจอเครื่องมือที่ใช้ได้เกิดขึ้นได้จริงในหลาย seed ไม่ใช่ seed เดียว)
- B2 ไม่ง่ายเกินไป: ผลต่างจับคู่ C3 − C0 ของ `functional_rate` มีขอบล่างของ 95% CI > 0

**H5 (สมบัติ vs. รหัสวัตถุ) วัดเฉพาะฝั่งการใช้:** C1 กับ C4 เลือกส่วนผสมด้วยกลไกเดียวกัน (Q ของส่วนผสม) ต่างกันแค่คีย์ของการใช้ (กลุ่มสมบัติ vs. รหัสวัตถุรายชิ้น) จึงตีความ C1 − C4 ได้เฉพาะฝั่งการใช้เครื่องมือ รายงาน C1 − C4 ของ `final_net_per_alive_tick`, `final_tool_use_rate` และ `functional_rate` ห้ามอ้างว่า H5 ครอบคลุมการสร้าง

## 6. กฎการเลือกค่า (ตรึงก่อนรัน)
ใช้เฉพาะข้อมูล S1 (seeds 1000–1049) ตามลำดับ
1. **คัดเซลล์ที่ผ่าน Gate**: เก็บเฉพาะเซลล์ที่ผ่านทั้ง Gate A และ Gate B
2. **เลือกตามสมรรถนะของ C1 ไม่ใช่ตามผลต่าง**: เลือกเซลล์ที่ค่าเฉลี่ย `final_net_per_alive_tick` ของ C1 สูงสุด (เทียบกับการปรับพารามิเตอร์ของ learner ให้ดีที่สุดตามปกติ ไม่ได้เลือกเซลล์ที่ทำให้ C1 − C2 ดูต่างมากที่สุด ซึ่งจะเป็นการตกปลาผลลัพธ์)
3. **เสมอ**: เซลล์ใดที่ค่าเฉลี่ย C1 ห่างจากเซลล์ดีที่สุดน้อยกว่า 1 SE ของเซลล์ดีที่สุด (SD ระหว่าง seed / √50) ถือว่าเสมอ แล้วเลือกตามลำดับ: tick น้อยกว่า → ε น้อยกว่า → q_init = 0 (เลือกค่าที่ง่ายและใกล้ค่าเดิมที่สุด)
4. รันเซลล์ที่เลือกบน S2 (seeds 1050–1099) ทั้ง 5 เงื่อนไข แล้วตรวจ Gate A/B ซ้ำบน S2 เพื่อรายงาน (ไม่ใช้เลือกค่าใหม่)

ค่า C1 ของเซลล์ที่ชนะใน S1 มีแนวโน้มสูงเกินจริงจากการเลือกจาก 16 เซลล์ จึงไม่ใช้เป็นหลักฐานหรือเป็นฐานของ power analysis (ใช้ S2 แทน) กฎ 1 SE เป็นกฎเลือกแบบประหยัดตามธรรมเนียม (one-standard-error rule) ไม่ใช่การทดสอบสมมติฐาน Gate ใน S1 เป็นการตรวจความเหมาะสมของสนาม ไม่ใช่ข้อสรุปทางวิทยาศาสตร์ จึงไม่ปรับ multiple comparisons ข้าม 16 เซลล์

## 7. Power analysis
- ใช้ผลต่างจับคู่ C1 − C2 ของ `final_net_per_alive_tick` จาก **S2** เท่านั้น
- ขนาดผล dz = ค่าเฉลี่ยผลต่าง / SD ของผลต่าง (ระหว่าง seed)
- เผื่อความไม่แน่นอนของ dz จาก 50 seeds ด้วยวิธี safeguard power (Perugini, Gallucci & Costantini, 2014): ใช้ dz_safe = เปอร์เซ็นไทล์ที่ 20 ของ dz จาก bootstrap (สุ่มเลือกคู่ seed แบบใส่คืน 10,000 รอบ, `random.Random(0)`) คือขอบล่างของช่วงความเชื่อมั่นด้านเดียว 80%
- จำนวน seed สำหรับ paired t-test สองทาง α = 0.05, power = 0.90 ใช้สูตรประมาณของ Guenther (1981) ซึ่งใกล้กับค่า noncentral-t จริง (ต่างไม่เกินราว 1–2 seed): n = ⌈((z₀.₉₇₅ + z₀.₉₀) / dz_safe)² + z₀.₉₇₅² / 2⌉ = ⌈(3.242 / dz_safe)² + 1.92⌉ แล้วยืนยันด้วยการจำลอง paired t-test 10,000 ครั้งที่ n นั้น (ข้อมูลปกติ, dz_safe) ว่า power ≥ 0.90 ถ้าไม่ถึงให้เพิ่ม n ทีละ 10
- ปัดขึ้นเป็นทวีคูณของ 10 ขั้นต่ำ 50 seeds
- ถ้า SD ของผลต่างเป็น 0: ถ้าค่าเฉลี่ยผลต่าง > 0 ใช้ขั้นต่ำ 50 seeds ถ้าเป็น 0 หรือติดลบให้หยุด
- ถ้า dz ≤ 0, dz_safe ≤ 0 หรือ n ที่ได้เกิน 2,000 ให้บันทึกใน 04 ตรง ๆ ว่าผลต่างเล็กเกินกว่าจะยืนยันได้ในขนาดที่ทำได้ และหยุดถามผู้ใช้ (ไม่เปลี่ยนตัวชี้วัดหลักเพื่อให้ได้ n เล็กลง)
- รันยืนยันจะใช้ seeds 5000 ถึง 5000 + n − 1 ทั้ง 5 เงื่อนไข ด้วย config ของเซลล์ที่เลือก

## 8. แผนสถิติของรันยืนยัน (ร่าง จะตรึงใน 05)
- สมมติฐานหลักหนึ่งข้อ: C1 − C2 ของ `final_net_per_alive_tick` > 0 ทดสอบด้วย paired t-test สองทาง α = 0.05 คู่กับ bootstrap 95% CI และ sign count (จำนวน seed ที่ C1 > C2)
- กลุ่มรอง (Holm correction ภายในกลุ่ม): C1 − C0 ของตัวชี้วัดหลัก; C1 − C2 ของ `functional_rate`, `reuse_delta`, `rebuild_rate`, `first_discovery_tick`
- เชิงพรรณนา (ไม่ทดสอบ): C3 − C0 (Gate), C1 − C4 (H5 ฝั่งการใช้), องค์ประกอบของอาหารสุทธิ, `level_a`, `level_b_run`
- ข้อสรุป "ค้นพบเครื่องมือ" ต้องมีหลักฐานหลายด้านพร้อมกัน: สมมติฐานหลักผ่าน และหลักฐานการค้นพบอย่างน้อยหนึ่งด้าน (อัตราระดับ A, การใช้ซ้ำแบบเลือก, การสร้างซ้ำ) ไปทางเดียวกันกับ C1 > C2

## 9. เงื่อนไขหยุดถามผู้ใช้
สร้าง `ysc-loop/STOP` พร้อมเหตุผล ถ้าเกิดข้อใดข้อหนึ่ง
- ไม่มีเซลล์ใดใน S1 ผ่านทั้ง Gate A และ Gate B
- ทุกเซลล์ใน S1 ให้ 95% CI ของ C1 − C2 (ตัวชี้วัดหลัก) คร่อม 0 (C1 ไม่ต่างจาก C2 ในทุกค่า)
- dz หรือ dz_safe บน S2 ≤ 0 หรือ n > 2,000 (ข้อ 7)
- ต้องแก้ `world/` หรือ `agents/`

## 10. สิ่งที่ห้ามทำ
- ห้ามเพิ่มเซลล์ เปลี่ยนตัวชี้วัดหลัก หรือเปลี่ยนกฎในข้อ 6 หลังเห็นผล ถ้าจำเป็นจริงให้บันทึกเป็น deviation ใน 04 พร้อมเหตุผลและผลของทั้งสองแบบ
- ห้ามตัดรันหรือ seed ใด ๆ ออกจากการวิเคราะห์ ยกเว้นตามกฎ censoring/การตัดที่ระบุไว้ในข้อ 5
- ห้ามรัน seeds 5000+ และห้ามใช้ seeds 0–99 เลือกค่า
