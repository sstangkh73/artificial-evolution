## ช่องทางโจมตีที่ต้องตรวจทุกข้อ
1. **การฝังคำตอบ:** มีการใช้ข้อมูลของ Dibble, มุมกรวย 136° หรือข้อมูลการตัด เป็นอินพุตหรือค่าที่จูนไว้ ทั้งทางตรงและทางอ้อมหรือไม่ มีตัวแปรที่ทำหน้าที่เป็น "ความคม" หรือ "คุณภาพหิน" แฝงอยู่ไหม
2. **การวัดที่เข้าข้างตัวเอง:** โค้ดใน `measure`/`validate` วัดสิ่งที่เกณฑ์ตั้งใจให้วัดจริงหรือไม่ เช่น มุมกรวยวัดจากรอยร้าวจริง นิยาม AOB ตรงกับของ Dibble มีการตัดข้อมูลหรือเลือกเฉพาะกรณีที่ผ่าน (cherry-pick) หรือไม่
3. **ฟิสิกส์ผิด:** สมการ หน่วย เงื่อนไขขอบ สมมติฐาน plane strain/stress และความยาว regularization ต้องคำนวณจากค่าวัสดุ ไม่ได้เลือกเอง ให้ตรวจพลังงานกับการอนุรักษ์ด้วย
4. **เทสต์อ่อน:** มีเทสต์ที่ผ่านได้แม้โค้ดผิดหรือไม่ เช่น assert ที่หลวมเกินไป หรือเทียบผลกับตัวมันเอง
5. **ผลไม่ทำซ้ำ:** รัน `python -m lithics.validate --only <ข้อที่สงสัย> --out physics-loop/.loop/rt-tmp/<ชื่อ>` ซ้ำอย่างน้อย 1 ข้อที่ไม่ใช่ V10/V11 แล้วเทียบผลกับ results.json (โฟลเดอร์นี้ git ignore ไว้ และเป็นที่เดียวที่เขียนไฟล์ได้ ไฟล์อื่นที่ถูกแก้จะถูก revert ทิ้ง)
6. **ความเปราะ:** เปลี่ยนอินพุตเล็กน้อยที่ไม่ควรมีผล เช่น seed ของ mosaic หรือความละเอียดใกล้เคียง แล้วดูว่าผลกลับด้านหรือไม่
7. **ความพร้อมของรอบ 2:** API ตรงตาม `spec/api.md` หรือไม่ และเอเจนต์จะเข้าถึงข้อมูลที่เป็นคำตอบได้หรือไม่

## รูปแบบคำตอบ
- **Blocking findings:** ปัญหาที่ทำให้ข้ออ้างใน 03 หรือผลผ่านของ V ข้อใดข้อหนึ่งเชื่อไม่ได้ แต่ละข้อให้ระบุ `ไฟล์:บรรทัด`, ปัญหา, หลักฐาน (คำสั่งที่รันและผลที่ได้) และสิ่งที่ต้องแก้
- **Non-blocking findings:** ปัญหาที่ควรแก้ แต่ไม่ทำให้ข้ออ้างหลักผิด
- **สิ่งที่ตรวจแล้วไม่พบปัญหา:** ระบุสั้น ๆ

ให้ FAIL เฉพาะเมื่อมี blocking finding อย่างน้อย 1 ข้อ ห้าม FAIL ด้วยเหตุผลด้านสไตล์

บรรทัดสุดท้ายของคำตอบต้องเป็นบรรทัดใดบรรทัดหนึ่งนี้เท่านั้น:
```
VERDICT: PASS
VERDICT: FAIL
```
